# Report 1 — redesign spec, 16 Aug 2026

Report 1 currently shows one number for the latest week. This adds a time
axis, shows forecast against outcome, and — the part that matters — shows
**when the model was wrong**.

Power BI Desktop runs in the Windows VM session, not here, so this is a
spec to apply there. All computation is already done in the warehouse; the
DAX stays thin on purpose.

## Data

`dbo.forecast_accuracy` (gold), built from `seeds/forecast_history.csv`,
generated by `research/backtest.py`. 706 weeks per fuel per horizon,
**Feb 2013 – 7 Aug 2026**, with target weeks running to 28 Aug 2026.

**Trained on Final, applied everywhere.** Those are different filters and
conflating them cost an earlier version its last 19 weeks. The model is fit
only on weeks MBIE has finalised; it is then *applied* to every week
including the Provisional ones, because the target
(`adjusted_retail_price`) has never been revised in 1,164 weeks and the
factor is revised by only ~0.5 c/L. Rows carry `input_status` so the report
can mark the difference rather than hide it.

**Six rows per fuel have no outcome yet** (`outcome_known = false`) — calls
for 14, 21 and 28 August whose week has not arrived. That is the live part,
and the reason the report exists. `actual_price` and every `err_*` are null
there by design, not by omission.

| column | meaning |
|---|---|
| `week_date` | week the call was made |
| `target_week` | week being called (`week_date` + horizon) |
| `fuel`, `horizon_weeks` | slicer dimensions (1, 2, 3 weeks) |
| `price_now` | actual pump price when the call was made |
| `actual_price` | what the price actually was at `target_week` |
| `pred_adl_ecm` | the model's call. **Use this one.** |
| `pred_naive` | "the price won't change" — the benchmark |
| `pred_report1_ish` | the current published formula, reconstructed |
| `abs_err_*` | absolute error per method |
| `mae_model_26w`, `mae_naive_26w` | trailing 26-week mean absolute error |
| `skill_26w` | `1 − model MAE / naive MAE`. **>0 = beating naive** |
| `input_status` | `final` / `provisional` — was the week's data finalised |
| `outcome_known` | false on the newest rows: the call is made, the week has not happened |

`skill_26w` is null until 26 weeks of history exist. Do not chart nulls as
zero.

## What it is, and the wording that has to appear on the page

**Every row is a walk-forward backtest, not a forecast that was published
at the time.** Each week's call was refit using only data available that
week, but the whole series was computed retrospectively on 16 Aug 2026.

Required on the page, near the title:

> Retrospective simulation. Each point shows what the model would have said
> that week using only the data available then. These are not forecasts
> that were published at the time.

And per `CLAUDE.md`, no point-forecast language anywhere: "the model would
have indicated", never "the price will be".

## Visuals

**1. Forecast against outcome** — line chart, `target_week` on the axis.
Two lines: `actual_price` and `pred_adl_ecm`. Optionally `pred_naive` as a
faint third. The reader sees the gap directly; no explanation needed.

**2. Error over time** — column chart, `target_week` on the axis,
`pred_adl_ecm − actual_price`, zero line marked. Positive = the model
called it high. Colour by sign.

**3. Skill** — the honest one. Area chart of `skill_26w` against a zero
line, filled green above and red below. This answers "is it working
lately", and it will show stretches where the answer is no. Average is
0.156 (petrol) and 0.169 (diesel) at two weeks, worst −0.98, and the model
leads naive in 83–86% of weeks.

**4. Cards** — current `skill_26w`, current `mae_model_26w` in c/L, and
share of weeks with `skill_26w > 0`.

**5. Slicers** — fuel, `horizon_weeks`, date range.

**6. Mark the live rows and the provisional ones.** Rows with
`outcome_known = false` should be visually distinct — dashed line, hollow
marker — so a call awaiting its week is never read as a hit. Rows with
`input_status = 'provisional'` should carry a lighter treatment too: the
inputs behind them may still be revised. Skill over the provisional stretch
currently reads 0.39 for petrol and 0.27 for diesel against 0.16 and 0.17
over the finalised history, but that is 17 weeks with both sides
provisional — not a result, and it should not be presented as one.

**Shade the background by `crude_vol_regime`** — now available on the
table, joined on `week_date` and `fuel`. Also present: `crude_episode_id`
(name the episode in a tooltip) and `crude_move_regime`.

What the shading shows, at two weeks:

| fuel | regime | avg skill | model MAE | naive MAE |
|---|---|---|---|---|
| diesel | normal | 0.179 | 2.85 | 3.69 |
| diesel | **high** | 0.141 | **5.96** | **7.64** |
| petrol | normal | 0.164 | 2.93 | 3.70 |
| petrol | **high** | 0.158 | **4.18** | **5.38** |

**The model keeps its edge in volatile weeks — but everyone's error
doubles.** That is the honest message for a reader deciding how much to
lean on this: a crisis does not make the model less useful than the
alternative, it makes precision unavailable to anybody. Worth saying in
words on the page, not just in a colour.

## DAX

```dax
Skill = AVERAGE ( forecast_accuracy[skill_26w] )

Model MAE 26w = AVERAGE ( forecast_accuracy[mae_model_26w] )

Naive MAE 26w = AVERAGE ( forecast_accuracy[mae_naive_26w] )

Weeks Model Ahead % =
DIVIDE (
    CALCULATE ( COUNTROWS ( forecast_accuracy ),
                forecast_accuracy[skill_26w] > 0 ),
    CALCULATE ( COUNTROWS ( forecast_accuracy ),
                NOT ISBLANK ( forecast_accuracy[skill_26w] ) )
)

Forecast Error =
VAR Actual = SUM ( forecast_accuracy[actual_price] )
VAR Called = SUM ( forecast_accuracy[pred_adl_ecm] )
RETURN
IF ( NOT ISBLANK ( Actual ), Called - Actual )
```

`Forecast Error` needs that guard. A plain subtraction returns `Called − BLANK`,
which DAX evaluates as `Called − 0` — so the three weeks that have no outcome
yet would each plot a column of roughly 250 c/L and dwarf every real error on
the chart. The guard is what makes the pending weeks absent rather than absurd.

Keep a single `horizon_weeks` selected in the slicer; averaging skill
across horizons mixes three different questions.

## Refresh

The seed is static. After each weekly data update:

```bash
python research/export_panel.py
python research/backtest.py
dbt seed --select forecast_history
dbt run --select forecast_accuracy --full-refresh
```

Then refresh the Power BI dataset. Provisional weeks are excluded from
training automatically — `backtest.py` filters on `status == 'Final'` — so
the series stops at the last finalised week and extends by itself as MBIE
finalises.

## Known limitation to state, not hide

The backtest runs on the current data vintage, so "data available at week
t" already contains MBIE's later corrections. Every method benefits
equally, so the comparison between them is fair; the absolute errors are
flattered by an unknown amount.
