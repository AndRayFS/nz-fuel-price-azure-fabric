# NZ Fuel Price Project — Azure/Fabric Rebuild

A scalable, multi-source rebuild of an oil-price-to-pump-price lag analysis,
originally done as a single R script, now running on Microsoft Fabric with
dbt as the transformation layer.

**Original analysis (R):** [nz-fuel-price-lag-analysis](https://github.com/AndRayFS/nz-fuel-price-lag-analysis)
— cross-correlation methodology, historical crisis periods, and the initial
2-week lag finding all originate there. This repo ports that logic onto a
proper pipeline and extends it.

**Companion posts:** [Part 1](https://www.linkedin.com/posts/andreimor_watching-the-news-about-the-latest-escalation-ugcPost-7485572175953920001-Uzat/) · [Part 2](https://www.linkedin.com/posts/andreimor_tree-ugcPost-7487295986630025216-b4Rj/) · [Part 3](https://www.linkedin.com/posts/andreimor_registration-costs-first-sql-ugcPost-7488350666168377346-Xctc/) · [Part 4 (dbt)](https://www.linkedin.com/posts/andreimor_microsoftfabric-dbt-dataengineering-share-7489268212065366017-QKU2/) · [Part 5 (Power BI)](https://www.linkedin.com/posts/andreimor_fuel-report-ugcPost-7491290122466971648-Qazx/)

## Architecture

```
MBIE weekly CSV (external source)
        |
        v
Microsoft Fabric workspace (Azure free account + F2 capacity)
        |
        v
Data Factory --(orchestrates)--> Lakehouse (bronze, raw snapshot)
        |                                |
        |                                v
        |                       Warehouse + dbt (silver -> gold)
        `--(orchestrates)-------------->|
                                         v
                                      Power BI
```

*(see `docs/architecture_diagram.png` for the illustrated version used in the posts)*

- **Bronze** (`bronze_lakehouse.mbie.weekly_prices`) — raw MBIE data,
  truncate + reload every run, schema-enabled Lakehouse.
- **Silver** (`silver_general`, `silver_fuel`) — long→wide pivot via a
  seed-driven macro (`variable_mapping.csv` maps source variables to
  destination columns — adding a variable is a CSV row, not a SQL rewrite).
- **Gold** (`lag_correlation`, `lag_resolved`) — cross-correlation by lag,
  period and factor, with an edge-guard that discards results sitting on the
  tested lag boundary (see `docs/architecture.md` for why). Also includes
  `resolved_slope`, `lag_confidence_gap` and `peak_prominence` — separating
  "is there a real historical pattern" from "do we know exactly which week
  it peaks in," which the dashboard surfaces as three plain-language
  questions instead of a single forecast number.
- **Volatility** (`factor_volatility`, `volatility_config`) — rolling
  crude-price volatility vs. a calm-period baseline, feeding a live "is this
  still a crisis?" indicator on the dashboard (deliberately a continuous
  signal, not a yes/no flag — see `docs/architecture.md`).
- **Snapshot** (`mbie_revisions`) — Type 2 tracking of MBIE's Provisional →
  Final revisions, excluding the LOESS-recomputed `Importer margin trend`
  column (see `docs/mbie_notes.md`).

Full lineage graph (generated by `dbt docs generate`, not hand-drawn) is in
`docs/lineage_graph.png`.

## Setup

Requires Python 3.11+ and the `dbt-fabric-samdebruyn` community adapter (the
official Microsoft adapter had version/ODBC friction on Apple Silicon — see
Part 3 for details).

```
python3.12 -m venv .venv
source .venv/bin/activate
pip install dbt-core dbt-fabric-samdebruyn
```

`~/.dbt/profiles.yml`:

```
nz_fuel_price_project:
  target: dev
  outputs:
    dev:
      type: fabric
      server: <your-warehouse>.datawarehouse.fabric.microsoft.com
      port: 1433
      database: analytics_warehouse
      schema: dbo
      authentication: CLI
```

```
dbt deps
dbt seed
dbt snapshot
dbt run
dbt test
```

**For weekly updates, always use `--full-refresh`:**
```
dbt run --select silver_general silver_fuel lag_correlation lag_resolved factor_volatility --full-refresh
```
A plain `dbt run` has been observed to not reliably pick up new bronze rows
for these specific models — not fully understood, but empirically confirmed
(see `docs/architecture.md`). Full command reference in `QUICKSTART.md`.

## Notes on methodology

- Lag correlation uses direct Pearson on overlapping pairs per lag, computed
  manually (Fabric Warehouse has no built-in `CORR()`), matching the original
  R script's approach rather than a naive windowed function.
- The maximum tested lag is capped per-period at `min(10, floor(period_weeks/3))`,
  same rule as the original R analysis, to avoid overfitting on short periods.
- `TRY_CAST` is used instead of `CAST` when parsing source values, with
  `not_null` tests as the safety net — a deliberate tradeoff over letting a
  single bad row fail the whole pipeline (see `docs/architecture.md`).
